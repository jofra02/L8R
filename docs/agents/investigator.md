# Investigator Agent

## Description
The Investigator Agent verifies specific hypotheses generated by the Hypothesis Agent. It operates with the **same full scenario context** as the Hypothesis Agent — topology graph, baselines, known changes, path analysis, and all hypotheses — ensuring it can reason about WHERE in the system to look and WHAT "normal" looks like. It follows a **configuration-first** approach.

## Role in Graph
- **Node Name:** `investigator_agent`
- **Upstream:** `supervisor` (routed when a hypothesis needs verification)
- **Downstream:** `enricher_agent` (to process the newly collected evidence)

## Inputs
- `state["hypotheses"]`: List of hypotheses. Targets the highest-ranked one with status `proposed` or `verifying`.
- `state["ticket"]`: Ticket details for context.
- `state["components"]`: List of identified components to scope tool arguments.
- `state["facts"]`: Collected facts for context injection.
- `state["evidence_refs"]`: Previous evidence (to avoid re-running blocked tools).
- `state["topology_edges"]`: Entity relationship graph for structural reasoning.
- `state["client_context"]`: Baselines (normal values) and known recent changes.
- `state["path_analysis"]`: Breakpoints, missing evidence, and suggested probes from hypothesis.

## Outputs
- `state["hypotheses"]`: Updates the status of the target hypothesis to `verifying`.
- `state["evidence_refs"]`: Appends new evidence snapshots collected from tool executions.
- `state["pending_requirements"]`: (on blocker) Adds HITL requirements for missing information.

## Context Injection (Full Scenario View)

The investigator receives the same rich context as the Hypothesis Agent, with **tighter truncation limits** since it focuses on a single hypothesis:

| Context | Source | Truncation |
|---|---|---|
| Topology graph | `topology_edges` | max 20 edges |
| Baselines | `client_context.baselines` | max 10 items |
| Known changes | `client_context.known_changes` | max 5 items |
| Path analysis | `path_analysis` | max 5 breakpoints |
| All hypotheses | `hypotheses` | max 8 items |
| Facts | `facts` | max 15 items |
| Evidence summaries | `evidence_refs` | last 8 items |

All formatting is done via shared utilities in `src/utils/state_formatters.py` (same functions used by `hypothesis.py`).

## Prompts

### 1. Verification Plan
**System:** "You are an expert IT Troubleshooter."
**Context injected:** Ticket, target hypothesis (summary + rationale), all hypotheses, components, facts, topology graph, baselines, known changes, path analysis.
**Goal:** Identify the most effective diagnostic action to prove/disprove the hypothesis.
**Key Instruction:** Configuration-first — prefer config inspection over live traffic analysis.

### 2. Tool Selection
**System:** "You are an expert Automation Engineer."
**Context injected:** Available tools + schemas, hypothesis (summary + rationale), components, facts, topology graph, baselines, path analysis, previous evidence, learned best practices.
**Goal:** Select the specific tool from search results and configure arguments.

**Guidelines:**
1. Analyze the Schema: Distinguish between mandatory and optional arguments.
2. Context Check: Look for parameter values (resource names, identifiers, scopes, endpoints) in Facts, Components, and Evidence.
3. Use Component IDs for `device`, `target`, `host` arguments.
4. Anti-Hallucination: If a mandatory parameter is missing from context, DO NOT invent it.
5. Blocked Tools: Check previous evidence for blocked tools. Select a discovery tool instead.
6. Safety: Read-only only.
7. Configuration-First: Prefer tools that read existing configuration over live traffic tools.

## Key Logic & Interactions

- **LLM Model:** Uses `LLM_MODEL_INVESTIGATOR` (e.g., `gpt-5.2`) — maximizing reasoning for hypothesis verification.

### Smart Argument Sanitization (Role-Based)
- **EXECUTORS** (device argument): firewall, router, switch, server, host, appliance, controller, gateway, hypervisor, node, cluster, database, storage, loadbalancer.
- **TARGETS** (target/destination argument): subnet, IP, URL, service, process, endpoint, user, application, container, pod, VM, instance.
- **Auto-Correction:** Only triggers when `match.id != val` — avoids no-op corrections.

### Tool Search
Uses Qdrant semantic search via `CapabilityRegistry.semantic_search_tools(intent)`. Falls back to keyword search if semantic returns nothing.

### Adaptive Execution
Tools executed via `AdaptiveExecutor` (with `customer_id` for tenant-scoped learning) which handles:
- Self-healing on tool failures (queries Qdrant for documented fixes).
- Missing dependency detection -> raises `MissingDependencyError`.
- Learned fixes persisted for future use.

### In-Flight Recovery
When a tool fails due to missing dependencies:
1. Saves failure evidence.
2. Attempts to resolve by selecting and executing a discovery tool.
3. If recovery succeeds, returns the resolution evidence for the next iteration.
4. If recovery fails, creates a `PendingRequirement` for HITL input.

### Interaction Flow
1. **Selection:** Picks the top `proposed` or `verifying` hypothesis.
2. **Context Building:** Formats topology, baselines, changes, path analysis, facts, hypotheses (shared formatters with truncation).
3. **Planning:** Asks LLM *what* to verify with full scenario context (output: search intent + reasoning).
4. **Search:** Queries Qdrant tool catalog with the intent.
5. **Configuration:** Asks LLM *how* to execute with topology + baselines + path analysis (output: tool name + args).
6. **Execution:** Runs the tool via AdaptiveExecutor, saves evidence.
7. **State Update:** Marks hypothesis as `verifying`, returns to graph.
