Quiero incorporar al proyecto una nueva funcionalidad completa de **Device Assessment**, inicialmente orientada a FortiGate.

## Contexto del proyecto

El proyecto actual tiene:

* Un agente basado en el patrón **ReAct**.
* Integración con distintos dispositivos mediante `mcp-gateway`.
* Capacidad para recibir y resolver tickets de mesa de ayuda.
* Backend, frontend y persistencia ya implementados.
* Herramientas MCP que permiten consultar configuración y estado operativo de dispositivos.

La nueva funcionalidad no debe implementarse como un script aislado. Debe tratarse como un **nuevo módulo de producto**, integrado de forma consistente con la arquitectura, autenticación, permisos, navegación, diseño visual, observabilidad y modelo de datos existentes.

Antes de modificar código:

1. Analizá la estructura completa del repositorio.
2. Identificá los patrones arquitectónicos actuales.
3. Localizá cómo se implementan:

   * Los agentes.
   * Las llamadas al `mcp-gateway`.
   * Los devices y customers.
   * Los jobs o ejecuciones en background.
   * La persistencia.
   * La API.
   * El frontend.
   * La autenticación y autorización.
   * Los logs, errores y auditoría.
4. Reutilizá los componentes y convenciones existentes.
5. No inventes una arquitectura paralela cuando ya exista una abstracción equivalente.

## Objetivo funcional

Implementar un módulo que permita ejecutar assessments técnicos sobre dispositivos FortiGate.

El flujo general debe ser:

1. El usuario selecciona uno o varios FortiGate.
2. Selecciona un tipo o plantilla de assessment.
3. El sistema ejecuta una recolección determinista de datos.
4. Los datos son obtenidos mediante `mcp-gateway`.
5. La evidencia recolectada se normaliza y almacena.
6. Un motor de evaluación aplica un manual de controles predefinido.
7. Opcionalmente, un agente LLM interpreta la evidencia siguiendo instrucciones estrictas.
8. Se generan findings, recomendaciones, scoring y un reporte.
9. El usuario puede revisar el resultado desde el frontend.

## Principio fundamental: recolección determinista

La recolección no debe depender de que el LLM decida libremente qué comandos ejecutar.

Cada assessment debe estar definido por una plantilla versionada que establezca previamente:

* Qué información se debe recolectar.
* Qué herramienta MCP se debe utilizar.
* Qué parámetros debe recibir.
* Sobre qué dispositivos aplica.
* Qué timeout utilizar.
* Qué resultado se considera válido.
* Qué datos son obligatorios u opcionales.
* Qué dependencias existen entre pasos.
* Cómo normalizar la respuesta.
* Qué controles utilizan cada evidencia.

Ejemplo conceptual:

```yaml
assessment:
  id: fortigate-security-baseline
  version: 1.0.0
  vendor: fortinet
  product: fortigate

collection_steps:
  - id: system_status
    tool: fortigate.get_system_status
    required: true

  - id: full_configuration
    tool: fortigate.get_configuration
    required: true

  - id: administrators
    tool: fortigate.get_admin_users
    required: true

  - id: interfaces_runtime
    tool: fortigate.get_interfaces
    required: true
```

No es necesario utilizar YAML si el proyecto ya posee otro mecanismo de definición, pero el modelo debe mantener esta separación conceptual.

## Separación de responsabilidades

Diseñá el módulo separando claramente:

### 1. Assessment Definition

Define:

* Metadata.
* Compatibilidad por vendor, producto y versión.
* Pasos de recolección.
* Manual de evaluación.
* Controles.
* Severidades.
* Scoring.
* Versión de la definición.

### 2. Collection Engine

Responsable de:

* Resolver el device.
* Ejecutar herramientas mediante `mcp-gateway`.
* Aplicar timeout, retries y límites de concurrencia.
* Registrar cada ejecución.
* Preservar la respuesta original.
* Normalizar resultados.
* Detectar datos faltantes.
* Evitar ejecuciones duplicadas.
* Permitir reintentar pasos fallidos.
* Mantener trazabilidad completa.

### 3. Evidence Store

Debe almacenar, como mínimo:

* Assessment run.
* Device evaluado.
* Collection step.
* Tool MCP utilizada.
* Parámetros.
* Inicio y finalización.
* Estado.
* Evidencia original.
* Evidencia normalizada.
* Error, cuando corresponda.
* Hash o identificador de integridad.
* Versión de la definición.
* Timestamp de recolección.

No almacenar secretos en texto plano. Aplicar redacción o sanitización cuando corresponda.

### 4. Evaluation Engine

Debe evaluar los controles de forma reproducible.

Prioridad de evaluación:

1. Reglas deterministas.
2. Parsers o evaluadores específicos.
3. Evaluación asistida por LLM solamente cuando el control no pueda resolverse de forma suficientemente confiable mediante reglas.

Cada control debería poder producir:

* `pass`
* `fail`
* `warning`
* `not_applicable`
* `not_evaluated`
* `insufficient_evidence`
* `error`

Cada resultado debe incluir:

* Identificador del control.
* Título.
* Descripción.
* Estado.
* Severidad.
* Evidencia utilizada.
* Explicación.
* Recomendación.
* Referencias.
* Confianza.
* Método de evaluación: `rule`, `parser`, `llm` o `hybrid`.

### 5. Assessment Agent

El agente no debe improvisar el alcance del assessment.

Debe recibir:

* Manual de evaluación.
* Controles aplicables.
* Evidencia previamente recolectada.
* Contexto del dispositivo.
* Formato de salida estructurado.

El agente debe:

* Evaluar solamente los controles solicitados.
* No inventar configuraciones.
* No asumir que una ausencia de evidencia representa incumplimiento.
* Diferenciar entre `fail` e `insufficient_evidence`.
* Citar exactamente la evidencia utilizada.
* Entregar una salida validable mediante schema.
* Evitar recomendaciones genéricas cuando exista evidencia específica.
* No ejecutar cambios sobre el dispositivo.
* No ejecutar herramientas adicionales, salvo que el diseño contemple explícitamente una fase controlada de recolección complementaria.

La lógica principal del assessment no debe depender exclusivamente del agente.

## Manual de assessment

Diseñá una estructura versionada para representar el manual esperado.

Cada control debería soportar campos equivalentes a:

```yaml
id: FGT-MGMT-001
title: Restrict administrative access
category: Management Plane
severity: high

description: >
  Administrative access should be restricted to dedicated management
  interfaces and trusted source networks.

required_evidence:
  - full_configuration
  - administrators
  - interfaces_runtime

evaluation:
  type: hybrid
  rule: management_access_rule
  llm_instructions: >
    Evaluate whether administrative access is exposed through production
    interfaces or unrestricted source networks.

expected_state:
  - Dedicated management interface when supported.
  - Trusted hosts configured for administrative accounts.
  - HTTPS and SSH restricted to required interfaces.
  - Insecure management protocols disabled.

references:
  - Fortinet Security Best Practices
  - Internal Security Baseline

remediation:
  summary: Restrict administrative access.
```

Las definiciones deben poder evolucionar sin invalidar assessments históricos.

## Criterios de aceptación

La implementación se considerará correcta cuando:

1. Un usuario pueda crear un assessment desde la UI.
2. Pueda seleccionar un FortiGate existente.
3. El backend cree una ejecución persistente.
4. La recolección use pasos predefinidos.
5. Las tools sean ejecutadas mediante `mcp-gateway`.

11. Los assessments históricos puedan consultarse.
12. El módulo respete permisos y tenants.
13. El flujo existente de tickets siga funcionando.
14. Los tests principales pasen.
15. La arquitectura permita incorporar nuevos dispositivos y vendors.

Cuando encuentres ambigüedades, tomá como referencia los patrones existentes en el repositorio y documentá el supuesto adoptado. No simplifiques silenciosamente requisitos importantes.
