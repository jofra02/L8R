# Architecture Design 002: Adaptive Tool Execution & Learning System (ATELS)

## 1. Objective
To implement an autonomous, self-correcting system that:
1.  **Heals**: Automatically retries failed tool executions by diagnosing errors and adjusting parameters.
2.  **Learns**: Captures successful usage patterns and "tricks" into a persistent Knowledge Base.
3.  **Applies**: Proactively retrieves this knowledge during future attempts to ensure "First-Time Right" execution.

## 2. Core Components

### A. The "Healer" (Adaptive Executor)
A wrapper around the standard `tool.run()` that implements a generic feedback loop.

**Logic Flow:**
1.  **Attempt 1**: Execute tool with generic parameters generated by Agent.
2.  **Check**: inspect output.
    *   *Success*: Return result. Pass to "Learner".
    *   *Failure* (Python Exception, API Error, or Empty Result): Trigger Diagnosis.
3.  **Diagnosis**:
    *   Input: `Tool Name`, `Args Used`, `Error Message`, `Tool Schema`.
    *   LLM Task: "Why did this fail? Suggest 1 specific fix to the arguments."
4.  **Retry Loop** (Max 2-3 retries):
    *   Apply fix -> Execute.
    *   If Success -> **Trigger Learning**.

### B. The "Learner" (Knowledge Distiller)
An asynchronous process that runs after a *recovered* failure (or optionally, after *any* novel success).

**Logic Flow:**
1.  Compare `Failed Args` vs `Successful Args`.
2.  Extract the "Rule" or "Trick".
    *   *Example*: "When using `get_resource_details`, always convert `resource_id` to integer."
    *   *Example*: "For `get_configuration`, the `scope` parameter is mandatory even if documentation says optional."
3.  Create a `ToolUsageInsight` object.
4.  Save to **Vector Store (Qdrant)** under `tool_knowledge` collection.

### C. The "Library" (Knowledge Retrieval)
A layer injected *before* the Agent selects tool arguments.

**Logic Flow:**
1.  Agent decides to use Tool X.
2.  System queries Qdrant: "Best practices for Tool X".
3.  Retrieved "Insights" are injected into the System Prompt or Tool Definition context.
    *   *Prompt Injection*: "REMEMBER: For Tool X, always do Y."
4.  Agent generates arguments using this specific knowledge.

## 3. Data Model

### ToolKnowledge (Vector Store)
```python
class ToolKnowledge(BaseModel):
    tool_name: str
    vendor: str
    scenario: str # "checking interface status"
    error_pattern: str # "AttributeError: ...", "404 Not Found"
    insight: str # The learned rule "Use 'root' vdom unless specified"
    good_example: Dict[str, Any] # The working args
    embedding: List[float] # For semantic search
```

## 4. Implementation Strategy (Phase 17)

### Step 1: ToolExecutor Wrapper
Create `src/core/adaptive_executor.py`.
- Replaces direct `await tool.run()` calls.
- Manages the retry budget.
- Calls the LLM for diagnosis (small, fast model like gpt-4o-mini).

### Step 2: Knowledge Store
Update `src/core/qdrant.py`.
- Add `tool_knowledge` collection.
- Add `get_tool_insights(tool_name, query)` method.

### Step 3: Integration
- **Evidence Collector**: Use `AdaptiveExecutor`. Inject insights into `_select_tools`.
- **Investigator**: Use `AdaptiveExecutor`. Inject insights into `tool_select_prompt`.

## 5. User Experience
- **Day 1**: System executes tools, hits common errors (400 Bad Request, missing params), enters Retry Loop, fixes them, and slows down slightly.
- **Day 2**: System remembers the fixes. It executes correctly on the first try. Speed increases. Reliability increases.
