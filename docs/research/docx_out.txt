Estado del arte y diseño de arquitecturas de AI agents para un SOC modular
Resumen ejecutivo
Los AI agents modernos (2020–2026) convergen hacia un patrón común: un LLM como “policy + reasoning layer” que planifica, usa herramientas (tool calling) y se apoya en memoria y retrieval para ejecutar flujos largos y auditables; el énfasis reciente está en (a) orquestación explícita y stateful (grafos/estado), (b) RAG “agentic” (retrieval adaptativo decidido por el agente), (c) multi-agent con roles para dividir tareas complejas, (d) evaluación de agentes con benchmarks realistas y (e) estandarización de tool/data connectivity (p.ej., MCP). [1]
Para un SOC operator / Tier-1–Tier-2 security analyst agent, el state of the art sugiere evitar “autonomía abierta” y preferir workflows acotados, con: ingest normalizado (ECS/CIM/OCSF), triage por etapas, evidence collection por conectores (SIEM/EDR/firewalls), enrichment (CTI/ATT&CK/STIX/TAXII), un decision engine gobernado por reglas/políticas, y action modules con RBAC + approvals (HITL) + auditoría completa. [2]
Para implementación modular, una recomendación práctica es LangGraph como orquestador principal (estado + persistencia + interrupts/HITL + “threads”), y FastAPI + MCP + FastMCP para exponer/consumir herramientas y convertir OpenAPI/Swagger en “tools” tipadas (con curación). [3]
Tendencias y papers state of the art
La evolución reciente puede resumirse en cuatro oleadas técnicas:
Primero, reasoning traces y prompting estructurado como base para descomposición y verificación: Chain-of-Thought Prompting (2022) abrió la puerta a “razonar en pasos” para tareas multi-step. [4] Luego, variantes deliberativas como Tree of Thoughts (2023) modelan búsqueda/ramificación (lookahead y backtracking) y Plan-and-Solve Prompting (2023) separa explícitamente plan de ejecución. [5]
Segundo, tool-using agents: ReAct (ICLR 2023) formaliza el bucle intercalado de Reason ↔ Act, mitigando alucinaciones al consultar fuentes externas; Toolformer (2023) entrena modelos para decidir cuándo invocar herramientas; y HuggingGPT (2023) usa un LLM como planner/router sobre un catálogo de modelos/herramientas. [6] En 2023–2024 aparece optimización de ejecución con planner–executor y paralelización: ReWOO (2023) desacopla reasoning de observations para bajar tokens; LLMCompiler (ICML 2024) compila planes a DAG y ejecuta funciones en paralelo. [7]
Tercero, memory y aprendizaje sin fine-tuning: arquitecturas con memoria episódica/reflexiva como Generative Agents (2023) y Reflexion (2023) muestran mejoras por “reflection + episodic memory”; MemGPT (2023) propone gestión multinivel de memoria inspirada en sistemas operativos para superar context windows limitados. [8] En paralelo, el “RAG clásico” (2020) se consolida como patrón de grounding, y en 2024–2025 emerge Agentic RAG (retrieval decidido/iterado por el agente) con taxonomías específicas. [9]
Cuarto, multi-agent y estandarización/operacionalización. Trabajos como AutoGen (2023), CAMEL (2023), MetaGPT (2023) y ChatDev (2023/2024) exploran coordinación por roles, SOPs y conversaciones estructuradas para dividir el trabajo (planificación, verificación cruzada, reducción de errores). [10] En 2025–2026 crecen surveys y benchmarks enfocados en evaluación y robustez de agentes (planning, tool use, memory, safety), y aparecen papers 2026 que sintetizan “agentic reasoning” como roadmap. [11]
En producción, además, crece la estandarización de integración LLM↔tools/data. El Model Context Protocol (MCP) se publica como protocolo abierto para “conectar” aplicaciones LLM con fuentes y herramientas mediante un modelo cliente-servidor; la especificación tiene versiones fechadas (p.ej., 2025-11-25). [12] Un punto operativo clave: la superficie de ataque aumenta (p.ej., prompt injection y tool misuse), y ya hay incidentes/vulnerabilidades reportadas en servidores MCP (ejemplo: fallas en un Git MCP server con posibilidad de file access/RCE por chaining y argument injection). [13]

Observabilidad; separación; permite “best tool for job”; buen fit SOC.
Overhead de integración; riesgo de “router errors”; gobernanza de herramientas.
MRKL (2022), HuggingGPT (2023). [19]
Planner–executor
Planner produce plan estructurado; executor invoca tools.
Trazabilidad; control por políticas; facilita paralelismo y HITL.
Sin buen planner, planes frágiles; requiere schema/representación de plan.
Plan-and-Solve (2023), LLMCompiler (ICML 2024). [20]
Decoupled reasoning from observations
Separar “razonar” de “consultar herramientas” para eficiencia.
Reduce tokens y latencia; robustez ante tool failures.
Riesgo de desalinear reasoning con realidad si el plan no incorpora evidencia.
ReWOO (2023). [21]
Memory-driven agents
Memoria episódica/semántica + reflexión para mejorar decisiones futuras.
Personalización; continuidad de casos; aprendizaje operativo sin fine-tuning.
Riesgo de “memory poisoning”; privacidad; necesidad de políticas de retención.
Reflexion (2023), Generative Agents (2023), MemGPT (2023). [22]
Retrieval-augmented (RAG)
Recuperación de evidencia (docs/logs) para grounding antes/durante generación.
Menos alucinación; trazabilidad a fuentes; útil para runbooks/CTI.
Calidad de index; leakage por embeddings; errores de retrieval = errores del agente.
RAG (2020); evolución a Agentic RAG (2025). [23]
Multi-agent (roles, debate, SOPs)
Varios agentes especializados colaboran; conversación/roles estructurados.
Divide tareas SOC: triage vs hunting vs remediation; verificación cruzada.
Coste; coordinación difícil; ataques/robustez multi-agent; “cascading hallucinations”.
AutoGen (2023), CAMEL (2023), MetaGPT (2023), ChatDev (ACL 2024). [10]
Hierarchical / skill library
Skills reutilizables + currículum + composición.
Buen fit para runbooks como skills; reutilización; menos drift.
Curación de skills; riesgo de acumular errores; control de versiones.
Voyager (2023). [24]
Evaluación y métricas “agent-grade” relevantes para SOC
Para SOC, medir “accuracy” de respuestas no alcanza: se necesita éxito end-to-end, robustez a entradas maliciosas, coste/latencia, y seguridad (acciones correctas y autorizadas). Surveys y benchmarks recientes formalizan dimensiones (planning, tool use, memory, reflection) y muestran que fallas típicas de agentes incluyen razonamiento largo débil, decisiones inestables y error propagation. [25]
Benchmarks genéricos útiles como referencia metodológica: AgentBench (agentes en entornos interactivos), WebArena (agentes web realistas), y benchmarks de tool learning (ToolBench/StableToolBench) para evaluar selección e invocación de herramientas. [26]
En el dominio cyber, hay surveys específicos sobre LLMs en cybersecurity y sobre LLMs aplicados a SOC, más trabajos académicos sobre triage Tier-1 con LLM agents e incluso colaboración multi-agent en incident response. [27]

Observaciones prácticas para SOC
1) La brecha principal no es “qué framework”, sino cómo gobernar herramientas: allowlists, schemas estrictos, timeouts, rate limits, y separación read-only vs write. Esto está directamente alineado con OWASP LLM01/LLM02 (prompt injection e insecure output handling). [80]
2) Para SOC es especialmente valioso un orquestador stateful + resumible + auditable: agentes que “pausan” para aprobación antes de ejecutar acciones de alto impacto (bloquear en firewall, aislar endpoint, reset creds). LangGraph documenta persistencia por checkpointers, threads, e interrupts para HITL. [81]
3) OpenAPI→tools es un acelerador útil pero requiere curación: la propia documentación de FastMCP advierte que agentes rinden mejor con MCP servers bien diseñados que con espejos automáticos de APIs complejas. [82]
Arquitectura propuesta para un AI agent tipo SOC operator
Componentes y responsabilidades
Arquitectura lógica (módulos):
Ingest y normalización - Ingest de alerts/events desde SIEM y collectors: syslog (RFC 5424) y/o APIs. [83]- Normalización a schemas operables para correlación y queries: Elastic Common Schema (ECS) y/o Splunk CIM; opcionalmente OCSF como esquema intermedio. [84]
Connectors - SIEM: Splunk (HEC/REST) y Elastic/Elasticsearch APIs. HEC describe envío por HTTP/HTTPS con tokens. [85]- Fuentes: syslogs, firewalls, switches, EDR/EPP (vía APIs), email security, IdP, cloud logs.
Triage pipeline - Deduplicación, agrupamiento (incident-building), y “alert typing”. - Evidence-first: antes de conclusiones, ejecutar recolección mínima de pruebas.
Evidence collection - Queries a SIEM (últimos N minutos/hours), timeline, procesos, logons, DNS, proxy, etc. - Snapshotting de evidencia y hashing (cadena de custodia ligera).
Enrichment - Mapeo a MITRE[86] ATT&CK tácticas/técnicas; uso de CTI feeds en STIX 2.1 y transporte TAXII 2.1. [87]- Rules: Sigma (formato genérico de detecciones), y reglas públicas (p.ej., Elastic detection-rules) para contexto/detección como código. [88]
Scoring y decision engine - Risk scoring: severidad, confianza (evidence coverage), impacto, exposición, repetición. - “Decision engine” con políticas: qué puede automatizarse vs qué requiere aprobación.
Action modules - Recommended actions y, bajo autorización, acciones: crear ticket, enriquecer incidente, bloquear IoC, aislar host, deshabilitar cuenta, etc. - Write actions siempre bajo RBAC y, por defecto, HITL.
Audit/logging y governance - Logging inmutable de: inputs, tools invocados, parámetros, outputs, decisiones y approvals. - Controles de seguridad: secretos, segregación de roles, rate limiting.
Security y RBAC - RBAC + “least privilege”; alineación con controles de auditoría y control de acceso (NIST). [89]
Protocolos y estándares a integrar
OpenAPI 3.1 para describir APIs y autogeneración de clientes/tools. [90]
syslog (RFC 5424) para logs de red/infra. [83]
Elastic ECS como schema de eventos (versión documentada en Elastic docs). [91]
Splunk CIM para normalización semántica en Splunk. [92]
STIX 2.1 / TAXII 2.1 para CTI. [93]
MCP para exposición/consumo estándar de tools/resources entre agentes y sistemas. [94]

Estrategia de implementación modular con LangGraph y FastMCP
Arquitectura de implementación recomendada
Recomendación primaria: LangGraph como “control plane” del agente. Motivos: soporte explícito de workflows long-running y stateful, persistence (checkpointers/threads), memory short/long-term, y HITL por interrupts; esto calza con SOC, donde el estado (incidente, evidencias, decisiones) debe persistir y ser auditable. [95]
Recomendación para interfaces de herramientas: FastAPI + MCP + FastMCP. FastAPI habilita APIs internas con OpenAPI automático; FastMCP permite (a) levantar MCP servers rápidamente, y (b) convertir OpenAPI/Swagger a MCP tools mediante from_openapi() o from_fastapi() o OpenAPIProvider. [96]
Ejemplo de integración OpenAPI/Swagger → MCP con FastMCP
FastMCP documenta creación desde OpenAPI y desde FastAPI. [97]
import httpxfrom fastmcp import FastMCPfrom fastapi import FastAPI# 1) Convertir un OpenAPI/Swagger existente a MCP (tools tipadas)client = httpx.AsyncClient(base_url="https://api.example.com")openapi_spec = httpx.get("https://api.example.com/openapi.json").json()mcp_api = FastMCP.from_openapi(openapi_spec=openapi_spec, client=client, name="Example API MCP")# 2) O: exponer tu propia API FastAPI como MCP (desde su OpenAPI)app = FastAPI(title="SOC Connectors API")mcp_from_fastapi = FastMCP.from_fastapi(app=app)
Puntos de diseño recomendados al “convertir”: - No exponer “toda la API”: usar route maps/tags para excluir rutas peligrosas (DELETE masivos, admin, secrets) o degradarlas a modo “read-only”. FastMCP explica el mapeo de rutas y exclusión. [98]- Publicar MCP servers por dominio: siem-read, edr-read, containment-write, ticketing-write, con scopes distintos (principio de menor privilegio).
Patrones de prompts y outputs para SOC
En SOC conviene maximizar estructuración y minimizar “texto libre” en pasos críticos:
Structured outputs (JSON estricto) para: clasificación del incidente, lista de evidencias requeridas, plan de queries, y “action request”. La motivación: reduce “insecure output handling” y facilita validación previa a tool execution (alineado con OWASP LLM02). [99]
Patrón planner–executor: el planner produce un plan en JSON (pasos + tools + parámetros + justificación breve + riesgo); executor valida contra policy (RBAC/allowlist) y ejecuta. Esto está alineado con la idea general de Plan-and-Solve y con compilación/ejecución estructurada tipo LLMCompiler. [20]
En etapas que interactúan con datos no confiables (logs, emails, URLs), tratar el contenido como data, no como instrucciones, mitigando prompt injection indirecta. [100]
Manejo de memoria y contexto
Separar tres capas (práctica común en agentes modernos):
Short-term memory: estado de “thread” (incidente actual, último tool output, decisiones intermedias). LangGraph lo persiste con checkpointers/threads. [101]
Long-term memory (cross-incident): “facts” operativos (p.ej., “este hostname es un mail relay legítimo”), tasas de falsos positivos por regla, preferencias de runbooks. LangGraph propone stores y acceso desde nodos en runtime. [31]
Evidence store: almacenamiento inmutable de snapshots (JSON/NDJSON, parquet) con retención y controles; no debe mezclarse con “memoria conversacional”.
Adicional: considerar arquitecturas de memoria inspiradas en MemGPT cuando el agente necesita navegar grandes volúmenes (playbooks extensos, historiales) sin saturar contexto. [102]
Seguridad y gobernanza
Controles mínimos recomendados:
Policy gates obligatorios antes de acciones “write”: RBAC, scopes por herramienta, approvals por severidad. OWASP LLM01/LLM02 son directamente relevantes. [99]
HITL por tool policy: pausar ejecución si la tool pertenece a “write class” o si el confidence score es bajo. LangChain/LangGraph documentan mecanismos de HITL/interrupts. [103]
Auditoría completa: registrar tool name, args, timestamps, outputs, actor, y decisión. NIST SP 800-53 rev5 (controles de auditoría y control de acceso) y prácticas de incident response actualizadas en SP 800-61 rev3. [89]
Threat model de tool connectivity: MCP y tool servers aumentan superficie; existen vulnerabilidades reportadas en servidores MCP (ejemplo Git MCP server) que refuerzan la necesidad de sandboxing, actualización y hardening. [104]
Pruebas y validación
Para SOC, validar por “casos” y por “propiedades”:
Offline regression suite: corpus de casos etiquetados (TP/FP) + expected actions. (Hay literatura/tesis de evaluación en triage Tier-1). [105]
Tool simulation: para evitar APIs inestables, usar mocks/caches (análogo a la motivación de StableToolBench). [106]
Adversarial testing: prompt injection indirecta en logs/CTI; validación de “no exfiltration”; y pruebas de output handling (OWASP LLM01/LLM02). [107]
Success metrics: tiempo a triage, tasa de reapertura, precisión inicial, y costos; hay reportes industriales de productividad en tooling SOC (p.ej., Security Copilot). [108]
Plan de prototipo con entregables y esfuerzo estimado
Supuesto: 1 engineer + 1 analyst SME, entorno SOC mediano con Splunk o Elastic, y acceso a un sandbox de logs.
Fase de descubrimiento y criterios - Entregables: catálogo de decisiones Tier-1 (classify/escalate/close), matriz de acciones (read vs write), threat model inicial, y esquema objetivo (ECS/CIM/OCSF).- Esfuerzo: 2–4 días.
MVP de ingest + connectors (read-only) - Entregables: microservicios FastAPI para siem_query, asset_lookup, ioc_reputation, case/ticket_create (en modo dry-run), cada uno con OpenAPI 3.1. [109]- Esfuerzo: 4–7 días.
Capa MCP para tools - Entregables: MCP servers generados y curados con FastMCP (from_openapi/from_fastapi), con tags/allowlists y timeouts. [97]- Esfuerzo: 2–4 días.
Orquestador LangGraph para triage - Entregables: grafo LangGraph con nodos: normalize→evidence→enrich→score→recommend; persistence habilitada con Postgres checkpointer/store. [30]- Esfuerzo: 5–10 días.
HITL, RBAC y auditoría - Entregables: policy gate para tool calls; approvals UI mínima (o integración con ticketing); audit log estructurado. [110]- Esfuerzo: 5–8 días.
Evaluación y hardening - Entregables: dataset de casos (≥200), métricas y report; red teaming de prompt injection; tool simulation/caching; runbooks versionados. [111]- Esfuerzo: 7–14 días.

[112]- LLM alternativo (API): Claude Opus 4.6 para tareas agentic largas (context amplio). [113]- Open-weight: Llama 4 (open-weight multimodal) y Mistral Large 3 (open-weight; modelos recientes). [114]- Embeddings: elegir un embedding model estable (p.ej., text-embedding-3-* en OpenAI API) si se usa vector DB. [115]- Orquestación: LangGraph; instrumentación/observabilidad con trazas y logs. [116]- Tools layer: FastAPI + MCP + FastMCP. [117]- Data: Postgres (state/checkpoints + store), objeto/S3 para evidencia, y SIEM como fuente de verdad. [30]- Cola/async: según escala, workers + (opcional) Ray para fan-out de enrichment/evidence. [62]
Riesgos, limitaciones éticas y de seguridad
Prompt injection (directa e indirecta): LLM-integrated apps no separan nativamente “data vs instructions”, habilitando ataques por contenido recuperado (indirect prompt injection). Esto es un riesgo estructural reconocido en literatura y guías. [118]Mitigación: treat-untrusted-data, sanitización, allowlists, separar canal de instrucciones, y policy gates pre-ejecución.
Insecure output handling: si un output del LLM alimenta directamente comandos/queries/acciones, puede convertirse en RCE o cambios no autorizados (OWASP LLM02). [99]Mitigación: schemas estrictos, validadores, escapes, dry-run, y approval.
Tool server / protocol expansion risk: MCP (y tool servers en general) mejora interoperabilidad, pero amplía superficie: hubo vulnerabilidades públicas reportadas en servidores MCP (Git MCP server) que derivan en file access/RCE al encadenar componentes. [104]Mitigación: hardening, actualización continua, sandbox, principio de mínimo privilegio por server, y separación de redes.
Hallucination / overconfidence: aún con tools, los agentes pueden inferir incorrectamente o cerrar incidentes sin evidencia suficiente; encadenamiento de errores es especialmente peligroso en SOC. Benchmarks muestran limitaciones en long-horizon reasoning y decision-making. [119]Mitigación: evidence thresholds, confidence scoring, fallbacks, y “abstain” cuando falta evidencia.
Privacidad y retención: memoria long-term y evidence stores pueden capturar PII/secretos; riesgo de exposición y de incumplir políticas internas. NIST AI RMF enfatiza gestión de riesgos y gobernanza. [120]Mitigación: minimización, redaction, retención limitada, y controles RBAC/auditoría.
Sesgos operativos: un agente entrenado/ajustado con datos históricos puede repetir sesgos (p.ej., priorizar ciertos tipos de alertas) y degradar servicio.Mitigación: métricas por segmento, monitoreo de drift, revisión humana periódica.
